## 📋 Resumen Ejecutivo

### Estado General

**SoftDomiFood** es un sistema de pedidos de domicilio (delivery) con arquitectura de microservicios distribuidos. El proyecto presenta una **base sólida** con buenas prácticas de containerización, separación de responsabilidades y documentación exhaustiva orientada a desarrollo con IA. Sin embargo, **existen múltiples problemas críticos** relacionados con:

- **Duplicación de código** entre `api/` (Python/FastAPI) y `backend/` (Node.js/TypeScript)
- **Inconsistencia en esquemas Prisma** entre `backend/` y `worker/`
- **Credenciales hardcodeadas** en múltiples archivos
- **Falta de manejo robusto de errores** y observabilidad
- **Ausencia de tests de integración y E2E** (solo tests unitarios de auth)
- **No existe CI/CD pipeline** para automatizar despliegues

**Tecnologías:** Python 3.11, FastAPI, Node.js 20+, TypeScript, React 18, PostgreSQL 15, RabbitMQ 3, Docker, Prisma ORM

---

### 🔴 5 Riesgos Principales

| # | Riesgo | Severidad | Impacto |
|---|--------|-----------|---------|
| **1** | **Duplicación masiva de servicios** (api/ vs backend/): dos APIs que implementan la misma funcionalidad en diferentes lenguajes | **CRÍTICO** | Mantenibilidad, deuda técnica exponencial, confusión del equipo |
| **2** | **Credenciales hardcodeadas** en docker-compose.yml, scripts y código (JWT_SECRET, DB passwords, RabbitMQ) | **CRÍTICO** | Vulnerabilidad de seguridad P0, exposición de secretos |
| **3** | **Inconsistencias en esquemas de datos** entre backend/prisma y worker/prisma (`paymentMethod` existe solo en worker) | **ALTO** | Errores en runtime, desincronización de datos |
| **4** | **Falta de pipeline CI/CD** y automatización de pruebas | **ALTO** | Riesgo de regresiones, deployments manuales propensos a errores |
| **5** | **Logging con print/console.log sin estructura**: no hay observabilidad centralizada ni métricas | **MEDIO** | Dificultad para debugging en producción, sin trazabilidad |

---

### ✅ 5 Quick Wins

| # | Quick Win | Esfuerzo | ROI |
|---|-----------|----------|-----|
| **1** | **Crear archivo `.env.example`** con todas las variables necesarias y documentarlas | **S** | Alto - Mejora onboarding y seguridad |
| **2** | **Implementar logger centralizado** (Winston/Pino en Node.js, structlog en Python) reemplazando print/console.log | **M** | Alto - Mejora observabilidad inmediata |
| **3** | **Agregar health checks HTTP** en API (/health con DB ping) y Worker | **S** | Medio - Mejora monitoreo |

### Flujo Principal: Crear Pedido

```
1. Usuario (frontend:3000)
   │
   ▼
2. POST /api/orders [JWT Token]
   │  - Valida token
   │  - Valida productos y dirección
   │  - Calcula total
   │
   ▼
3. Inserta en DB (asyncpg)
   │  orders, order_items
   │
   ▼
4. Publica mensaje a RabbitMQ
   │  Queue: order_queue
   │  Payload: { orderId, userId, items, total, addressId }
   │
   ▼
5. Worker consume mensaje
   │  - Simula preparación (5 segundos)
   │  - Actualiza estado: PREPARING
   │
   ▼
6. Cliente puede consultar estado
   GET /api/orders/:id
```

## 🔍 Calidad de Código

### Hallazgos por Categoría

#### 1. Duplicación / Código Muerto

| Archivo/Módulo | Evidencia | Impacto |
|----------------|-----------|---------|
| **backend/** vs **api/** | Carpeta backend/ completa implementa las mismas funcionalidades que api/ (auth, products, orders, addresses, payments) | **CRÍTICO** - Confusión, mantenimiento doble, riesgo de divergencia |
| [backend/src/controllers/auth.controller.ts](backend/src/controllers/auth.controller.ts) | Duplica lógica de [api/routers/auth.py](api/routers/auth.py) | Deuda técnica alta |
| [backend/prisma/schema.prisma](backend/prisma/schema.prisma) vs [worker/prisma/schema.prisma](worker/prisma/schema.prisma) | Esquemas casi idénticos pero con diferencias (paymentMethod) | Errores potenciales en producción |

**Recomendación P0:** Decidir stack único (Python o Node.js) y eliminar el otro. Si backend/ está en desuso, documentarlo y archivarlo.

---

#### 2. Complejidad Ciclomática

| Archivo | Función/Método | Líneas | Problema |
|---------|----------------|--------|----------|
| [api/routers/orders.py](api/routers/orders.py#L27-L134) | `create_new_order` | ~107 | Función "Dios": validación, cálculo, persistencia y publicación en un solo método |
| [worker/src/index.ts](worker/src/index.ts#L55-L182) | `startConsumer` | ~127 | Manejo de conexión, errores y consumo en un solo bloque |
| [api/init_db.py](api/init_db.py) | Script completo | 240 | SQL embebido como string literal (difícil de mantener) |

**Recomendaciones:**
- Refactorizar `create_new_order` en funciones más pequeñas: `validate_order`, `calculate_total`, `persist_order`, `publish_to_queue`
- Separar lógica de conexión RabbitMQ en módulo reutilizable
- Migrar SQL de init_db.py a migraciones Alembic (Python) o Prisma (Node.js)

---

#### 3. Code Smells

**Hardcoded Values:**

```python
# api/services/auth_service.py:12
SECRET_KEY = os.getenv("JWT_SECRET", "your-super-secret-jwt-key-change-in-production")
```
🔴 **Problema:** Default inseguro expuesto en código

```yaml
# docker-compose.yml:22-23
RABBITMQ_DEFAULT_USER: admin
RABBITMQ_DEFAULT_PASS: admin123
```
🔴 **Problema:** Credenciales hardcodeadas

**Uso de `any` en TypeScript:**

```typescript
// worker/src/index.ts:40
} catch (error: any) {
```
⚠️ **Problema:** Pierde type safety, debería ser `unknown` o crear tipo específico

**Print/Console.log en producción:**

```python
# api/main.py:24
print("🚀 Inicializando base de datos...")
```
```typescript
// worker/src/index.ts:27
console.log(`📦 Procesando pedido: ${message.orderId}`);
```
⚠️ **Problema:** No hay logger estructurado, dificulta auditoría y debugging

---

#### 4. Acoplamiento y Cohesión

| Módulo | Problema | Nivel de Acoplamiento |
|--------|----------|-----------------------|
| [api/routers/orders.py](api/routers/orders.py) | Importa directamente `services.database_service` y `services.rabbitmq` | Medio-Alto |
| [worker/src/index.ts](worker/src/index.ts) | Lógica de negocio mezclada con infraestructura RabbitMQ | Alto |

**Recomendaciones:**
- Implementar **Dependency Injection** (usar FastAPI Depends de forma más consistente)
- Separar capa de infraestructura (RabbitMQ, DB) de lógica de negocio
- Crear interfaces/abstracciones para servicios externos

---

#### 5. Manejo de Errores

**Problemas detectados:**

```python
# api/main.py:38-44
except Exception as e:
    print(f"⚠️  Error al verificar/inicializar base de datos: {e}")
    import traceback
    traceback.print_exc()
    print("   Continuando de todas formas...")
```
🔴 **Problema:** Swallow exceptions sin propagación, puede ocultar fallos críticos

```typescript
// worker/src/index.ts:103-108
} catch (error: any) {
    console.error(`❌ Error procesando pedido ${message.orderId}:`, error);
    throw error;
}
```
⚠️ **Problema:** No hay retry logic ni dead-letter queue para mensajes fallidos

**Recomendaciones:**
- Implementar middleware global de manejo de errores en FastAPI
- Agregar dead-letter queue en RabbitMQ para mensajes fallidos
- Implementar circuit breaker para dependencias externas

# Resumen ejecutivo (página 1)
- Proyecto multi-servicio (FastAPI + RabbitMQ + worker Node + dos frontends Vite + backend Express legado) orientado a pedidos. Arquitectura funcional pero con solapamientos (API Python vs Express), configuraciones inseguras por defecto y escasa observabilidad.

- La API Python tiene validaciones básicas y separación por routers/servicios; el backend Express duplica responsabilidades y carece de validaciones y manejo de errores robusto.
- Frontends almacenan tokens en `localStorage`, comparten endpoints sin separación clara cliente/admin y usan hooks de autenticación simulada, lo que genera riesgos de sesión y coherencia.
- Testing: carpeta `qa_automated` con scripts y pruebas (auth, seguridad, carga), pero no hay integración CI ni métricas de cobertura reportadas en el repo.
- Observabilidad limitada a logs de consola; sin métricas, tracing ni alertas.

# Arquitectura AS-IS
- Diagrama textual:
  - Cliente web (Vite React) ↔ API FastAPI (`/api/*`) ↔ PostgreSQL; publica mensajes a RabbitMQ → Worker Node actualiza pedidos.
  - Admin web similar.
  - Backend Express paralelo expone `/api/*` con Prisma sobre mismo Postgres (posible conflicto).
  - Docker Compose orquesta Postgres + RabbitMQ + api + worker + dos frontends; sin gateway.
- Flujo principal (request → capas → datos):
  1. Front → axios (`VITE_API_URL`) → FastAPI routers.
  2. Router valida token (HTTPBearer), delega a services DB (asyncpg/SQLAlchemy) → Postgres.
  3. En creación de pedido, publica en RabbitMQ; worker consume y actualiza estado en Postgres.
  4. Legacy Express expone rutas CRUD directas Prisma → Postgres (sin cola).

# Calidad de código
- Hallazgos:
  - Validaciones parciales en Express: rutas `product.controller.ts` y `order.controller.ts` no sanitizan/valida tipos ni límites; uso directo de body. (`backend/src/controllers/*.ts`)
  - Manejo de errores genérico, sin códigos específicos ni logs estructurados; captura `any`. (`backend/src/controllers/*`, `worker/src/index.ts`)
  - Hooks de auth en front simulados, no integran real backend → incoherencia de estado. (`frontend/src/hooks/useAuth.js`, `admin-frontend/src/hooks/useAuth.js`)
  - Prisma schema sin índices/paginación; posibles consultas completas. (`backend/prisma/schema.prisma`)
  - Versión del repo incluye `api/venv` y `__pycache__`, afectando limpieza.
- Duplicación / complejidad / anti-patrones:
  - Duplicación de dominio y rutas entre FastAPI y Express (dos backends).
  - Token secret fallback a `'secret'` en Express y a default débil en FastAPI.
  - Uso de `localStorage` compartiendo `token`/`clientToken`/`adminToken` sin aislamiento.

# Seguridad
- Hallazgos + severidad:
  - P1: Credenciales y secretos hardcodeados en `docker-compose.yml` y `README` (DB, RabbitMQ, JWT). Sin rotación.
  - P1: JWT secret fallback débil (`process.env.JWT_SECRET || 'secret'`) en Express; default en FastAPI (`your-super-secret...`). Riesgo de token forgery.
  - P1: Tokens en `localStorage`, sin expiración/refresh ni CSRF protection. (`frontend/src/utils/api.js`)
  - P2: Sin rate limiting, ni lockout en login; bcrypt con salt por defecto pero sin políticas de password.
  - P2: Worker expone URL de RabbitMQ en logs (aunque mascara pass en algunos casos).
- Manejo de secretos y configuraciones:
  - `.env` no usado; secretos en compose y código.
  - No hay gestor de secretos ni separación dev/prod.

# Performance
- Prisma y SQLAlchemy sin índices ni paginación; riesgo de scans completos.
- Worker procesa 1 mensaje a la vez (`prefetch(1)`) → throughput limitado.
- `Math.random` en pagos simulados y `setTimeout` en worker introducen latencia artificial.
